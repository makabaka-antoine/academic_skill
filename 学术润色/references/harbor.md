# Harbor execution

1. Read `/input/case.json` and the task file supplied with it (commonly `/input/task.md`). Take `case_id` from the input exactly, including its type. Read the actual `output_contract`, requested deliverable, and named attachments, including any on-disk material it references. Where the contract defines fields by list, schema, descriptor, or examples, use its exact nesting, names, values and types. A local illustration or this Skill's internal audit schema is never the official contract. Honor case-requested filenames and preserve bilingual order or tables when specified.
2. Use `/app/work` for extraction, term tables, plans and candidates. Resolve this Skill's assets from its installed directory (normally `/skills/weekly-skill`), never from the author's computer. Resolve runtime tools through the available `environment/resources.yaml` and observed tools. Read materials at their actual paths. Use the supplied text/PDF/render/OCR tools where the case needs them. Offline reading and ordinary text polishing work without any account or network service.
3. Save actual usable results in `/app/output` once the first meaningful portion is complete. For a long case, write the covered scope, results and unresolved scope with the applicable partial status, then improve the same output as you progress. Maintain full requested coverage: if using sections, keep track of each and reassemble in order. A submission answering a format or citation task should still be the actual requested output, not a plan to produce it.
4. Write `/app/output/result.json` in UTF-8 with `case_id` and every field required in the source `output_contract`. Populate the required main result field with content or relative artifact paths as the contract specifies. If a destination field needs an array or object, write that type. Link only files that exist and were inspected. Preserve the contract's own status vocabulary. Place source, change and uncertainty data in their designated fields. If the contract has no room for essential provenance, use a compact `evidence.json` alongside the requested output, referenced from an allowed field or artifact list if applicable. Keep audit contents outside the editable manuscript.
5. Before finishing, open the final `result.json` and each declared artifact. Run `scripts/check_result.py` with the actual case and final result when available. Use its report to catch absent keys or wrong types, then manually compare every requirement with the result, including requirements expressed in prose. Ensure that source locations point to material read, change records match the editable version, and each requested preview was actually generated and inspected. A compile or a field check gives only the evidence it performed.

## Evidence and coverage

Use the case's field names. In a companion record where needed, keep the following information. Compress repeats by linking a verified source occurrence to multiple changes. Preserve each change's own original, revision and reason.

| Record | Minimum useful content |
|---|---|
| Input/source | Source file, version when known, and a locator such as PDF page + quote, table + row/column, original line span, or user prompt paragraph. Record read scope. |
| Changes | Stable change ID, original source locator, original and revised sentence, one or more classes, specific reason, and any affected anchor IDs. Useful classes are grammar, syntax, punctuation, terminology, register, clarity, translation, and format. |
| Fact/source mapping | Important quantity or proposition, original source locator and evidence relation, and destination in the final file. Record what was checked for terminology, citations and figure/table links. Mark source-provided if retained without independent verification. |
| Coverage | Requested, reviewed, edited and unresolved units with locations. Record the actual script/build/visual checks and their scope. |
| Uncertainty | `material_missing` for absent evidence or inputs, `judgment_unresolved` for conflicts or ambiguous meaning, `execution_failed` for a tool/build/format failure. Describe affected units and any retained candidate. |

If the case supplies a scoring requirement or checklist, use it as an acceptance check against the actual output. Conditions, runtimes and official scores come from the platform. Save source-based partial work and a precise issue if a required material or tool is unavailable.

Continue on clear units when a judgment cannot be resolved from the materials. Retain the affected source wording and record an author query instead of waiting for a reply from an unattended harness. Use the contract's status based on what was delivered. An anticipated query can coexist with a complete editorial deliverable when the case allows that. A missing requested section, file or preview must be visible in the status or scope record.
